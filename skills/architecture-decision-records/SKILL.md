# Architecture Decision Records

Inherits `docs/SKILL_CONTRACT.md`.

A small file format that turns every non-trivial architectural decision into a durable,
queryable artifact. The chain has memory; ADRs are the memory's structural backbone.
When a future session asks "why are we using X?", the answer is an ADR, not a Slack
scroll.

## When to use

- a non-trivial architectural choice is locked (framework, library, database, deployment
  shape, protocol, auth provider, queue, model tier routing);
- `/plan-loop` or `/revise-plan` sets a decision whose consequences survive the session;
- an existing decision is superseded or deprecated - the new ADR links back via
  `Supersedes:` and the old ADR's `Status` moves to `superseded`;
- a doubt is resolved and the resolution becomes long-lived system policy.

## When NOT to use

- tactical implementation choices that the next refactor will replace;
- one-off fixes whose rationale lives in the commit message;
- product-strategy decisions - those belong in `plan/main_plan.md`, not in `docs/adr/`.

## File Layout

```
docs/
  adr/
    README.md           # index of all ADRs (auto-generated by /adr-list)
    0001-record-architecture-decisions.md
    0002-use-postgres-row-level-security.md
    0003-...md
```

Each ADR is numbered sequentially. The index in `README.md` lists every ADR by status,
title, and link. New ADRs do not renumber old ones.

## Required Schema

```markdown
# <number>. <short title>

- **Date:** <YYYY-MM-DD when the decision was made>
- **Status:** proposed | accepted | superseded | deprecated
- **Deciders:** <who decided; named roles, not "the team">
- **Supersedes:** <ADR numbers, comma-separated; leave blank if none>
- **Superseded by:** <ADR numbers, comma-separated; leave blank if none>

## Context

<what forces are at play; what constraints exist; what evidence was weighed.>
<2-4 paragraphs; cite EVIDENCE_LOG entries where relevant.>

## Decision

<the choice itself; one paragraph. State the choice crisply.>

## Alternatives Considered

| Alternative | Why rejected |
|---|---|
| <option A> | <concrete reason> |
| <option B> | <concrete reason> |
| <option C> | <concrete reason> |

## Consequences

### Positive
- <observable benefit, with the metric or test that proves it>
- <observable benefit>

### Negative
- <cost, risk, or lock-in we accept>
- <cost, risk, or lock-in>

### Risks
- <risk that becomes real if X happens>
- <risk + mitigation>

## Lifecycle

- <Date>: proposed.
- <Date>: accepted after <who approved>.
- <Date>: superseded by ADR-NNNN; reason.
```

## Workflow

### 1. Detect the decision signal

ADR-worthy decisions are signalled by language in the user's message or in the chain's
output:

- explicit: "let's go with X", "we decided Y", "approved";
- implicit: comparing two frameworks with rationale, picking one library over another,
  naming a stack layer in `plan/main_plan.md` `## Tech Stack` that wasn't there before,
  changing a deployment target.

A decision whose rationale survives the session but whose artifact does not is exactly
what ADRs solve.

### 2. Resolve the existing ADR if relevant

Before writing a new ADR, search `docs/adr/`:

```
grep -l "<framework or pattern name>" docs/adr/*.md
```

If an existing ADR covers the same surface, the new ADR either:
- `Supersedes:` it (the prior decision is replaced; update its `Status` to `superseded`),
  or
- extends it (write a new ADR that references the prior one in **Context**).

Do not silently contradict an existing ADR.

### 3. Number it

Look at the highest existing `NNNN-<title>.md` and increment by 1. Do not renumber.

### 4. Write the file

Use the schema above. Fill every required field. Empty fields fail the validation
`scripts/validate_outputs.py` runs.

### 5. Update the index

Append a row to `docs/adr/README.md`:

```
| 0001 | accepted | Record architecture decisions | 2026-09-01 |
| 0002 | accepted | Use Postgres row-level security | 2026-09-04 |
```

If `docs/adr/README.md` does not exist, create it with the same column header.

### 6. Reference the ADR from elsewhere

When the chain uses the decision in a later plan or task, cite the ADR number:

```
plan/features/007-revenue-recovery/spec.md:
  Database: Postgres with row-level security (ADR-0002).
TASKS.yml:
  - id: T-007-03
    spec: ADR-0002
    acceptance: [tenant_id always scoped server-side; tested with cross-tenant denial]
```

This is the mechanism that prevents the chain from rediscovering a decision.

## Output

- New ADR file at `docs/adr/NNNN-<slug>.md`
- Updated `docs/adr/README.md`
- Existing ADR's `Status` updated to `superseded` (if applicable)
- One-line citation in `plan/main_plan.md` `## Tech Stack` (if the decision is at stack level)
- One-line entry in `state.db` via the chain's session-closeout log

## Anti-Patterns

- An ADR that explains "what" without explaining "why" (deciders cannot re-derive intent
  later).
- An ADR with no alternatives considered. If there were no alternatives, the decision is
  trivial and does not need an ADR.
- An ADR with no consequences section. A decision without consequences is a press release.
- Multiple decisions in one ADR. One decision per file.
- A `proposed` ADR that never moves to `accepted`. Either accept or delete.
- An ADR that contradicts an existing one without `Supersedes:`. The chain will believe
  both, and one is wrong.

## Related Skills

- `plan-loop/phases/council.md` - pressure-test the decision before locking it;
- `revise-plan` - apply a free-form correction; ADRs are the canonical place for the
  rationale it captures;
- `codebase-design` - vocabulary and module shape that ADRs reference;
- `plan-canvas` - visuals that surface architecture decisions before they are locked;
- `decision-ledger` (if/when added) - append-only ledger for multi-rollout decisions.


## Stop Conditions and Rollback

A mutating skill declares when to halt and how to revert, before it runs. This section
is required by the canonical skill contract (`docs/SKILL_CONTRACT.md` "Risk and approval")
and is the E3 pattern adopted in round 4.

### When to stop

- **Three failed attempts at the same step.** Retrying past three means the
  hypothesis is wrong, not the execution. Stop, record what was tried, and
  escalate to the user as a doubt.
- **A change introduces more errors than it resolves.** Net negative progress
  is a regression, not a fix. Revert the change; record the failure mode.
- **A gate fails that the plan said must pass.** A gate is a contract; a
  failing gate is the chain telling you the work is not done. Stop and resolve.
- **The active task's `acceptance` criteria become unreachable** because of
  upstream changes. The plan is no longer valid; the task needs re-design,
  not more attempts.
- **Cost drift outside the budget.** A skill that consumes tokens or dollars
  unboundedly is a runaway; stop and report.

### When to escalate to the user

- **High-risk external actions** (publish, deploy, spend, destructive,
  privileged) require explicit user approval per `AGENTS.md` #5. The skill
  prepares the change, names the risk, and waits.
- **A blocker that is human-owned.** The blocker is a question only the
  user can answer (a stakeholder's call, a missing credential, a sign-off).
  Record it in `DOUBTS.md` and `HANDOFF.md`; do not invent an answer.
- **A goal-direction change.** The plan no longer matches what the user
  wants. The chain halts; the user re-plans.

### Rollback path

- **A single-task rollback** is `git revert <task-sha>` (or `git restore` for
  staged-only changes) followed by re-running the active feature's
  `converge-report` to confirm the rollback did not regress the rest of
  the build.
- **A multi-task rollback** is a feature-level revert: identify the feature
  commit range from `.loop/active-feature.json`, revert the range, then run
  `feature-converge` to confirm the surface is clean.
- **A state-only rollback** (files, configs, but no code) is a `git restore
  <path>` + `git clean -fd <path>` for the recorded paths. The skill's
  output records which paths it touched; the rollback reverses exactly
  those.
- **A data-only rollback** is database- and tenant-scoped; record the
  affected rows in the change record, run the inverse migration, and
  verify the diff matches the change record before declaring done.
- **A deploy rollback** is the prior version's artifact promoted through
  the same path the deploy took; `cicd-release/SKILL.md` carries the
  per-deploy rollback procedure.

A rollback that cannot be performed in one step is a planning problem.
Stop and re-plan; do not chain partial rollbacks.
